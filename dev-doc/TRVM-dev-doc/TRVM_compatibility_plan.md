# TRVM Compatibility Plan (Single File)

> Цель: для любой Solana-программы P, любого входа I и любого допустимого параллельного планирования — TRVM(P, I) обеспечивает **исходную совместимость** (Source Compatibility) с SVM по логике исполнения, логам, compute units, ошибкам и CPI-семантике. Криптографические артефакты (PDA, хэши) могут отличаться, сохраняя детерминизм внутри сети TRIAD.

## Легенда статуса
- [ ] Не начато
- [~] В процессе
- [x] Готово

## 1. Формализация совместимости
- [ ] Чёткое определение эквивалентности TRVM↔SVM (state/logs/CU/errors/CPI/side-effects).
- [ ] Тестовое утверждение для любого допустимого параллельного планирования.
- [ ] Ограничение: наблюдаемое поведение идентично при том, что планировщик/память/исполнитель/потоки отличаются.

**Definition:** ∀ программ P, ∀ входов I, ∀ допустимых планов π:  
TRVM(P, I, π) ≡ SVM(P, I) по **Projected State** (логика данных аккаунтов, логи, CU, ошибки, CPI семантика).  
Криптографические выходы (PDA, хэширования) основаны на Blake3 и являются детерминированными внутри TRIAD, но не обязаны быть побайтово идентичными Solana.

## 2. Архитектура TRVM как ядро + Solana Compatibility Layer (SCL)
- [ ] Определить границу: TRVM Formal Execution Kernel vs SCL адаптер спецификации.
- [ ] Описать потоковую модель (CPU решает ветвления/CPI/ошибки, GPU — чистое вычисление без недетерминизма).
- [ ] Прописать: SCL — не VM, а адаптер спецификации; SVM — диалект TRVM.
- [ ] Зафиксировать: не «Solana runtime на GPU», а новая VM с формальной совместимостью.

## 3. Священный контракт SVM (нельзя менять)
### 3.1 ABI и байткод
- [ ] Исполнение BPF bytecode Solana (bit-compatible).
- [ ] Calling convention / stack layout / register usage / syscall ABI.
- [ ] ELF sections, relocation, program-derived addresses (PDA).
### 3.2 Syscalls
- [ ] Реализовать полный набор syscalls (sol_log*, sol_mem*, sol_invoke_signed, sysvars rent/epoch/stake/clock и др.).
- [ ] Идентичные коды ошибок и borrowing rules.
- [ ] Отдельно: mutability/aliasing при CPI, ошибки на дубли/readonly/writable.
### 3.3 Account borrowing & mutability
- [ ] Writable/readonly, duplicate refs, borrow conflicts, CPI aliasing — логически эквивалентная модель.
- [ ] Воспроизвести исторические quirks/edge-cases SVM (borrow checker, порядок syscalls, CPI, realloc timing) — без «переосмысления».

**SVM quirks (обязательны к воспроизведению):**
- [ ] Borrow checker: странные комбинации readonly→writable, дубликатов, CPI aliasing, invoke_signed + sysvar; поведение должно совпадать с SVM даже если нелогично.
- [ ] Порядок/момент вызова syscalls и realloc: один сдвиг — несовместимость.
- [ ] CPI edge-cases: дубли аккаунтов, смешение readonly/writable, PDA/Signer флаги, пересечения через sysvars.

## 4. Где можно менять (и нужно)
### 4.1 Планировщик исполнения
- [ ] DAG/interference scheduler: построение зависимостей, speculative parallelism, deterministic rollback.
- [ ] Порядок наблюдаемых эффектов соответствует SVM.
- [ ] Правило: конструктивная интерференция = параллелизм, деструктивная = схлопывание к приоритетной tx.
- [ ] Планировщик ≠ greedy locks; banking loops/ретраи — заменены волновым планированием.
### 4.2 Compute Units → Wave Cost Model
- [ ] Внутренний wave-based cost/GPU/SIMD.
- [ ] Внешнее соответствие отчёта CU: доказать эквивалентность метеринга.
- [ ] Требование: публично репортится тот же CU, даже при SIMD/GPU агрегации.
### 4.3 Память / Zero-copy
- [ ] Внутренняя модель (SoA, page-aligned arenas, GPU buffers, copy-on-write snapshots, shared RO pools).
- [ ] Гарантии pointer stability + bounds идентичны видимым правилам SVM.
- [ ] Прописать realloc semantics, lifetime = instruction scope, pointer stability.

## 5. CPU + GPU детерминизм
- [ ] Жёсткое правило: GPU не принимает решений, только чистые функции/редукции.
- [ ] Дет. редукции и bulk-synchronous исполнение.
- [ ] CPU принимает ветвления, ошибки, CPI; GPU = pure function accelerator.

## 6. Масштабирование
- [ ] Линейное масштабирование (±2–3%) при отсутствии глобальных локов и shard-local state.

## 7. Адаптация бенчей
- [ ] Перенести/адаптировать бенчи Solana под TRVM, фиксировать метрики (state parity, CU, latency, throughput).

## 8. Acceptance Criteria
### 8.1 Автоматически
- [ ] Replay TRIAD history → идентичный state root.
- [ ] Fuzz CPI depth.
- [ ] Randomized account aliasing.
- [ ] Syscall edge cases.
### 8.2 Публично
- [ ] Compatibility test suite.
- [ ] Performance regression dashboard.
- [ ] Determinism proofs (STARK или экв.).

## 9. Delta vs SVM (прозрачные отличия)
- [ ] Зафиксировать отличия (планировщик, память, внутренний исполнитель), подтвердить идентичность внешних эффектов.
- [ ] Указать: всё «несвященное» (scheduler, memory, execution engine, потоковая модель) может отличаться, но видимый контракт — как в SVM.

## 10. Трассировка и проверяемость
- [ ] Определить формат логов/trace для сверки TRVM vs SVM.
- [ ] Инварианты для аудита (например, хеши состояния после батча, счетчики CU).

## 11. Threat Model
- [ ] Покрытые классы атак: недетерминизм исполнения (запрещён), недетерминизм FPU (запрещён), расхождения CU/логов/состояния между узлами.
- [ ] Некрытые/временно out-of-scope: timing side-channels, кэшевые сайд-чаннелы, физические атаки.
- [ ] Для каждой категории — ожидаемое поведение (fail/abort) и тестовый охват.

**Заявка:**  
Покрываем: (а) любые источники недетерминизма исполнения/плавающей запятой/распараллеливания; (б) несогласованность CU/логов/состояний между валидаторами; (в) неправильную семантику syscalls/CPI/borrow.  
Out-of-scope (пока): timing/cache side-channels, физические атаки, экономические атаки вне протокола.  
Ответ системы: детерминированный отказ/abort при нарушении контракта; тесты: fuzz недетерминизма, совпадение хешей состояния, golden CU/logs.

## 12. Допустимое параллельное планирование (определение)
- [ ] Определение: любое планирование, при котором граф зависимостей транзакций (по аккаунтам/borrow rules/CPI) сохраняет topological order совместимый с семантикой SVM, а детерминированный результат = SVM.
- [ ] Ограничение: планирование не может нарушать сериализуемость по аккаунтам и не может вводить недетерминизм за счёт гонок на mutables.
- [ ] Формально: если транзакции имеют конфликт по write/read на одном аккаунте, их относительный порядок в плане должен соответствовать SVM-эквиваленту; все другие перестановки допустимы.

**Формально:**  
Пусть G — граф конфликтов (ребро, если пересечение write/read одного аккаунта или CPI aliasing). План π допустим, если является топологической сортировкой G и приводит к той же трассе эффектов, что и любая допустимая сериализация SVM. Все коммутирующие операции могут свободно переставляться; конфликтующие обязаны сохранять порядок, эквивалентный SVM.

## 13. Non-goals
- [ ] Не пытаемся быть byte-for-byte runtime Solana (внутренние реализации могут отличаться).
- [ ] Не повторяем banking stage.
- [ ] Не повторяем leader schedule.
